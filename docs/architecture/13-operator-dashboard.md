# 13 — Operator Dashboard (Portal)

App: `apps/portal` → `https://portal.luxrocket.example`. API: `/api/portal/v1`, same origin, path-routed to Django (no CORS; host-only `__Host-` cookies). Realm `OPERATOR`. `frame-ancestors 'none'`.

## 1. Tenant isolation (enforced, not cosmetic)

1. Staff session carries `realm=OPERATOR` and `operator_id`; there is no request parameter that selects an operator. (A staff member of two operators has two accounts — OQ-28 if group operators need switching.)
2. Every portal request: middleware builds `TenantContext` → opens transaction as role `portal_rw` → `SET LOCAL app.operator_id = '<uuid>'` → Postgres RLS (`FORCE ROW LEVEL SECURITY`) filters every tenant table.
3. Repositories also filter explicitly (defence in depth); foreign ids return `404`.
4. Exports are generated by a worker running with the same role and context; download links are single-use, 15 min, bound to the requesting user.
5. Caches keyed `op:{operator_id}:…`.
6. Automated test: for every portal endpoint × every HTTP method, a request from operator B referencing operator A's ids returns 404 and leaks no timing-significant difference (best effort).

## 3. Modules

### 3.1 Overview
Game availability per environment; integration health (wallet success rate & p95 latency 1 h/24 h, circuit-breaker state, webhook success); recent activity (rounds, bets, players — 24 h); transaction failures & pending credits; open reconciliation discrepancies; commercial performance (turnover, wins, GGR, actual RTP with sample size; supplier fee estimate per contract).

### 3.2 Integration management
| Feature | Behaviour |
|---------|-----------|
| Environment & IDs | Operator public id, environments, API base URLs, play origin, platform public keys |
| Credentials | Create Ed25519 (upload public key, or generate in browser and download private key once) or HMAC (secret shown **once**); list metadata; rotate (overlap ≤ 14 days); revoke (step-up auth) |
| Domains | Add exact origins; verify via DNS TXT `_luxrocket-verify.<host>` or `/.well-known/luxrocket-verify.txt`; unverified domains are not added to `frame-ancestors` in production |
| Webhooks | Endpoints, event types, signing key, test delivery, delivery log with replay |
| Wallet endpoint | URL & timeouts (within platform bounds); **conformance test** runs the full wallet suite (idempotency, duplicates, rollback-of-unknown, credit-after-session-end) against sandbox |
| Connectivity tests | Signed ping to their wallet; session-create dry run |
| Logs | Operator API calls & wallet attempts (redacted), filter by correlation id/transaction id |
| API docs | Rendered OpenAPI + embedding guide + SDK reference |
| Sandbox | Virtual-credit players, simulated wallet toggle, fault injection toggles |

### 3.3 Game configuration (only what the platform permits)
| Setting | Operator-editable? | Bound |
|---------|-------------------|-------|
| Game availability on/off (per environment) | ✓ | — |
| Enabled currencies | Choose from platform-approved list | — |
| Min / max stake, default stake, quick-stake chips | ✓ | Within platform ceilings per currency |
| Max win per bet, round exposure | Request only (platform approves) | Platform ceilings |
| Auto cash-out availability | ✓ | — |
| Locale default, number format, display alias masking | ✓ | — |
| Show cash-out feed / round stats | ✓ | — |
| Session reminder interval / time-limit defaults | ✓ | RG minimums set by platform/jurisdiction |
| House edge, curve, outcome algorithm, max multiplier, betting window | ✗ | Platform ruleset only |
| Anything about an active round | ✗ | Impossible |
Changes create a new `operator_config_version`, take effect at the next round for new bets, and are audited.

### 3.4 Transaction reporting
Bets, cash-outs, settlements, refunds, wallet transactions (with operator references), round history (with verification link), reconciliation daily reports. Filters: date range (UTC or operator TZ display), player id, currency, status, round, amount range. Downloads: CSV/XLSX (async job, emailed link optional), schema documented and versioned.

### 3.5 Users & access
| Role | Capabilities |
|------|-------------|
| OP_OWNER | Everything in the tenant incl. users & credentials |
| OP_ADMIN | Users (except owners), config, domains, webhooks |
| OP_DEVELOPER | Credentials, domains, webhooks, wallet endpoint, logs, sandbox |
| OP_FINANCE | Reports, reconciliation, downloads |
| OP_SUPPORT | Bet lookup by player/bet id, round verification (no exports) |
| OP_VIEWER | Read-only overview & reports (no player-level detail) |
MFA: optional per user by default; operator can enforce for the tenant; **mandatory** for credential and user management actions (step-up) regardless (OQ-29 to make it fully mandatory). Session list & revoke; audit history of the tenant's own actions.

## 4. Permissions enforcement
DRF permission class (role → permission) + service-level checks; RLS for data scope; UI hides what's unauthorised but security never relies on it.

## 4a. As built (v1)
- API `backend/luxrocket/portal` at `/api/portal/v1`; UI `apps/portal` (static export behind nginx, which proxies
  `/api/portal/` on the same origin and blocks every other `/api/` path).
- Session: `__Host-lr_portal` cookie (HttpOnly, Secure, SameSite=Strict, Path=/), 8 h absolute, 30 min idle; the
  operator is taken from the session only. Mutations additionally need `X-LR-Portal: 1` and a same-origin `Origin`.
- MFA: TOTP (RFC 6238) — optional to enrol, **required** (and fresh within 10 min) for credentials, wallet and
  user management. WebAuthn is the platform-staff requirement (doc 12) and comes with that console.
- Isolation today rests on session-derived tenancy + explicit filters, verified by `test_portal.py` (every
  parameterised route with another tenant's ids → 404; list routes scanned for leaks; route inventory test).
  Postgres RLS remains the planned second layer.

## 5. Acceptance criteria
- AC-OP-1: Cross-tenant test suite (§1.6) passes for 100 % of endpoints; CI blocks new endpoints without a cross-tenant test (route inventory check).
- AC-OP-2: Secrets displayed exactly once; subsequent API responses never include them (test).
- AC-OP-3: Config changes outside bounds are rejected server-side with `CONFIG_NOT_PERMITTED`.
- AC-OP-4: Wallet conformance test detects each injected contract violation in the reference faulty-wallet suite.
- AC-OP-5: Report totals equal ledger-derived totals for the same filter (reconciliation test).
- AC-OP-6: WCAG 2.2 AA.
